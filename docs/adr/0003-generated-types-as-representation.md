# ARD 0003 — Generated schema types are the in-memory representation

## Status

**Proposed.** It reverses what ARD 0001 called its load-bearing decision, so the reasoning below is
mostly an argument with that record.

**Revisions.** v0 — initial draft.

## Context

ARD 0001 decision 6 says the TUI defines its own struct per editable section, decodes only the
section in focus, and **never** decodes a whole sheet into
`internal/dto/v1alpha/character.CharacterSchema` or re-encodes one from a decoded value. Its reason
was concrete: `mapper.validateSheet` decodes into that type purely to enforce required fields and
enums and then throws the result away —

```go
func validateSheet(raw json.RawMessage) error {
	var sheet schema.CharacterSchema
	if err := json.Unmarshal(raw, &sheet); err != nil {
		return fmt.Errorf("%w: %w", common.ErrInvalid, err)
	}
	return nil
}
```

— so the bytes that reach storage are the client's own, and a field the generated type has no home
for still survives a round trip. A client that unmarshalled, edited a field, and marshalled back
would delete every such field on the first save.

PSD-0001 decides the opposite. §5.3 gives the model a `doc *character.Document` — "in-memory decoded
schema document" — and D9 (§6) makes the type tree a build artifact of the schema, generated by
`omissis/go-jsonschema` with hand-written exceptions, on the reasoning that a schema change which
removes or renames a field should be a compile error rather than silent data loss.

Two facts about the repository as it stands matter more than either argument.

- **The codegen already exists, and it is already the only generator.** `internal/generate.go` runs
  `go tool go-jsonschema` over `docs/jsonschema/character/v1alpha/*.schema.json` into a single
  package, and `github.com/atombender/go-jsonschema` is a `tool` dependency in the root `go.mod`.
  D9 is not a new adoption; it is a proposal to *rely* on something already built.
- **The generated tree is not a passive struct tree.** It emits `UnmarshalJSON` methods that enforce
  required fields and validate enums, and it materializes schema defaults during decode. So
  "decode the document" is already a validation event with opinions, whether or not anyone wanted one.

The question is therefore narrower than ARD 0001 or PSD-0001 pose it: **is the generated tree the
representation the editor mutates, or only a gate — and if it is the representation, how many trees
are there and which validator is authoritative?**

## Decision

**One generated tree, promoted from gate to representation. The editor decodes the whole document
into it, mutates it, and re-encodes it. The compiled JSON Schema stays the authority on validity, and
it runs before the decode, not after.**

### 1. One tree, kept where it is generated

`internal/dto/v1alpha/character` remains the only generated tree, and `internal/character` — the
package PSD-0001 §5.3 names — holds the *behaviour* around it: loading, validating, the derive
package (ARD 0005), and the hand-written exceptions below. It does not re-declare the types.

Generating a second tree from the same schema files into a second package would double the
regeneration surface and create two Go types for one contract, which is the drift D9 exists to
prevent. That the surviving path reads `internal/dto/...` while an application package imports it is
mildly odd, and it is the honest description of what the tree is: an artifact of the versioned
schema, generated per `[namespace]/[version]` exactly as `internal/generate.go`'s package comment
describes. A record proposing to move it should be a record about the `dto` boundary, not a side
effect of this one.

### 2. Validate first, then decode — PSD-0001 §5.3's order is backwards

§5.3 says loading is "decode-then-validate-then-hydrate". It has to be the other way around.

The generated `UnmarshalJSON` rejects an out-of-range enum with `invalid value (expected one of …)`
and a missing required field with `field pool_id in SlotPool: required`. Those are Go type errors
naming a Go type. §6 promises a validation failure surfaces "the failing JSON Pointer paths", and
only `santhosh-tekuri/jsonschema` produces those. If the decode runs first, every schema-invalid
document fails with the wrong error, and the read-only-with-banner path §6 specifies — which needs to
know *where* the document is wrong — cannot be built.

So: read the bytes, validate against the compiled schema, then decode. A decode error after a
successful validation is a bug in the generated tree or in the vendored schema copy, and should be
reported as one rather than as a bad document.

### 3. The compiled schema is the authority; the generated tree is a convenience

Where the two disagree, the schema wins and the tree is what changes. This matters for the two
hand-written exceptions, which exist because the generator cannot express the construct at all:

| construct | what the generator emits | hand-written as |
| --- | --- | --- |
| `slotPool.slots` — `patternProperties: {"^[1-9]$": …}`, `additionalProperties: false` | `type SlotPoolSlots map[string]interface{}` | `map[int]SlotCount` with `MarshalJSON`/`UnmarshalJSON` enforcing the 1–9 key range |
| `conditionInstance` — `allOf`/`if`/`then`/`else` requiring `level` for Exhaustion, forbidding it otherwise | `ConditionInstanceLevel *int`, with the conditional nowhere | a struct with a nullable `Level` plus `Validate()` carrying the conditional |

Both live in a clearly marked `types_manual.go` excluded from regeneration, and both are convenience
checks that let a screen refuse bad input inline. Neither is a second source of truth: the compiled
schema still runs at load and at save.

### 4. The schema copy and the generated tree are both CI gates

The vendored schema at `internal/character/schema/character.schema.json` is byte-identical to the
project document, asserted by a `go generate` check. Regenerating the tree and running
`git diff --exit-code` is a CI job. A schema edit that lands without a regenerated tree is the
failure mode D9 is buying protection against, and it is only protection if something fails.

## Consequences

- **ARD 0001's guarantee is deliberately given up, and something must replace it.** A whole-document
  round trip through generated structs cannot preserve what the structs have no field for. The
  replacement is the round-trip corpus in §10 and ARD 0009 — fixtures that go load → mutate → save →
  validate and are compared byte-for-byte where the schema permits. A guarantee enforced by tests is
  weaker than one enforced by never decoding, and that is the trade.
- **The editor gains compile-time knowledge of the sheet, which is the entire point.** Nine section
  screens (§7.2–§7.10) and a derive package (ARD 0005) reach named fields. Under ARD 0001 each of
  those was a hand-written struct plus a hand-written decode per section.
- **`mapper.validateSheet` and the TUI now depend on the same type for different purposes.** The
  daemon uses it as a gate and discards the value; the TUI keeps the value. A change made for one
  consumer's benefit — a hand-written exception, say — is visible to the other.
- **`play_log` must exist in the schema before this tree is relied upon**, which is ARD 0004 and why
  it is Phase 0 pre-work.
